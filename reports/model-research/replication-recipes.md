# RoBERTa / DistilBERT replication and bounded GPU pilot

Updated 2026-10-02. This supplements `comparison.md`. No training, GPU launch, purchase, weight download or external pickle execution was performed. Public notebooks were parsed as JSON, not executed. CSV review text was streamed to calculate aggregate dataset checks; it was not retained.

**Recommendation:** benchmark existing weights first. If a training pilot is still useful, bhavyagiri now has the clearest recoverable recipe, while DistilBERT is a useful smaller-architecture experiment with incomplete historical settings. Replicating a published IMDb validation result and improving the product benchmark are separate objectives. Neither architecture nor model-card F1 establishes apples-to-apples superiority.

## Dataset preparation: recovered source plus independently checked artifacts

The [author's EDA notebook](https://github.com/bhavya-giri/spoiler-alert/blob/ce0688f0a69bd0fc7d6d28b2dd01645505c2c89f/notebooks/EDA%20and%20Split.ipynb) reads Rishabh Misra's `IMDB_reviews.json` (573,913 rows in saved output). It retains `review_text` and `is_spoiler`, converts Boolean labels to integers, and renames them `text` and `label`: **0 non-spoiler, 1 spoiler**. The full corpus output reports 150,924 positives and 422,989 negatives.

Preparation is a **stratified 5% sample**, then **stratified 80/20 train/validation**. The notebook calls `np.random.seed(42)` before the first split, whose `random_state` is omitted; the second split explicitly sets `random_state=42`. Exact resampling depends on original row order, RNG execution history and environment, so reuse the published CSVs for replication. No text cleaning, class balancing, class weights, deduplication or grouping by movie/user appears in this preparation code. Movie/user IDs are dropped before splitting. Saved CSV indices survive as a blank-header column (`Unnamed: 0` after pandas import); they are not input features.

The [published subset](https://huggingface.co/datasets/bhavyagiri/imdb-spoiler/tree/9da61fd253654914524f7eba74b0fa6461c0f974/data) has two files, `train.csv` and `valid.csv`; the dataset service exposes the latter as `validation`. Its card has an Apache-2.0 tag but little preparation detail. Exact audit results at this revision:

| Split | Rows | Label 0 | Label 1 | Positive fraction |
|---|---:|---:|---:|---:|
| Train | 22,956 | 16,919 | 6,037 | 26.30% |
| Validation | 5,740 | 4,231 | 1,509 | 26.29% |

No blank texts; one extra exact duplicate row within train; **one distinct exact review text occurs in both train and validation**, despite zero shared source indices. This is an observed small leakage issue, not proof of broader deduplication. Near-duplicates and title/user overlap were not measured; CSVs lack title/user fields. The always-negative validation baseline is about **73.71% accuracy**, which contextualizes reported 78% accuracy. A weighted F1 is not positive-class F1.

See `subset-audit.json` and `audit_public_subset.py` for the aggregate audit; source hashes remain in memory only. For literal reproduction keep original splits and disclose overlap. For a clean comparison deduplicate before building new splits and identify the experiment as a modified protocol. Do not report that modified score as a reproduction of the original card.

## Critical metric check: 0.773 is not spoiler-class F1

The audited validation set contains **1,509 positives among 5,740 reviews**. Reported accuracy `0.7832752613240418` corresponds to **1,244 errors** (4,496 correct). For the same labels and predictions, `FP + FN = 1244` and `TP <= 1509`, so positive-class binary F1 is bounded by:

`F1_spoiler = 2TP / (2TP + FP + FN) <= 3018 / (3018 + 1244) = 0.708118`.

Thus **0.773021 is numerically incompatible with spoiler-class binary F1 on this split and those predictions**. This bound is not an estimate of actual spoiler F1; the actual value may be lower. Accuracy alone does not identify precision, recall or the confusion matrix.

The author's pinned [metric code](https://github.com/bhavya-giri/spoiler-alert/blob/ce0688f0a69bd0fc7d6d28b2dd01645505c2c89f/notebooks/Fine-Tuning.ipynb) explicitly uses `f1_score(labels, preds, average="weighted")`; its saved output reproduces the card values, including `test_f1=0.7730205935926013`, on `trainer.predict(validation)`. Therefore **weighted averaging is directly evidenced here, not merely guessed**. The model card alone omits this definition. Different averaging, another split/version, or different predictions could explain such a mismatch in general, but the recovered notebook specifically supports weighted F1 for the cited result. Exact correspondence between the currently hosted weight artifact and that notebook execution remains unverified. Do not advertise this result as “77% spoiler F1,” or compare it directly against binary positive-class or macro F1.

## Concrete recipes for a future run

**A. Closest documented RoBERTa replication.** Use the pinned CSV revision unchanged, only `text`/`label`; initialize base RoBERTa with two labels and reproduce the notebook's tokenization map (batch 1,024, padding/truncation enabled). Use per-device train/eval 16, three epochs, LR 2e-5, weight decay .01, evaluate each epoch, and compute weighted F1 and accuracy after the final epoch. Record additional spoiler precision/recall/F1 separately. Recover or explicitly declare schedule, warmup, accumulation, optimizer betas/epsilon and seed choices before running. Do not silently inherit contemporary Trainer defaults or claim exact numerical reproduction. Disable hub pushes and third-party logging. A GPU-compatible pinned environment must be validated rather than blindly reinstalling old requirements.

**B. DistilBERT replication-style run.** Reuse the same pinned splits and labels; initialize `distilbert-base-uncased` plus binary head; use LR 2e-5, train/eval 16, one epoch, seed 42, linear schedule, and eval/save at steps 500 and 1000. Keep final model as well as the checkpoint with minimum validation loss, reporting both so selection is transparent. Declare max length 512, padding policy, accumulation, weight decay, warmup, optimizer implementation and precision as **new choices** where the original is unknown. Reproducing .7794 is not guaranteed and is not a product success criterion.

**C. Zritze LR1-inspired control, not exact replication.** RoBERTa-base, LR 1e-5, batch 8, three epochs, seed 42, linear schedule, evaluation every 500 steps. Because the actual dataset is undisclosed, applying this recipe to bhavyagiri data is a new experiment. It is less useful than A/B for the first bounded pilot; defer it to avoid an unplanned hyperparameter sweep.

## Recommended bounded hosted NVIDIA GPU pilot (proposal only)

Use one hosted **24 GB NVIDIA GPU**, with an RTX 4090-class Runpod Pod as a candidate if available at launch. This is a proposed memory target, not a tested fit/runtime guarantee. [Runpod](https://www.runpod.io/product/cloud-gpus) offers selectable GPU Pods; verify the actual device, rate and storage charges before provisioning. For a no-purchase smoke test, an available Colab GPU is an alternative, but its [FAQ](https://research.google.com/colaboratory/faq.html) explicitly says hardware and resource availability vary. Do not promise a T4 or completion time.

Proposed limits: **one GPU, two model runs, one seed, no sweep; two wall-clock hours or US$10 total, whichever limit is reached first.** These are proposed budget caps, not a quote or authorization to spend. Calculate a shutdown deadline from the actual GPU and storage rate; include setup/evaluation time and a shutdown margin. Stopping a training process is insufficient: shut down the billed Pod, export wanted artifacts, and remove chargeable storage when finished, following [provider lifecycle guidance](https://docs.runpod.io/pods/manage-pods).

For a clearly labeled **modern pilot**, fill unknowns explicitly: AdamW (betas .9/.999, epsilon 1e-8), linear decay, zero warmup, weight decay .01 for RoBERTa and 0 for DistilBERT, full-model updates, max length 512, dynamic per-training-batch padding, seed/data seed 42 set before model initialization, gradient clipping 1.0, and fp16 mixed precision. Start at microbatch 4 with accumulation 4 (effective batch 16 on one GPU), eval batch 4; if memory fails, microbatch 2/accumulation 8 while preserving effective batch. These are controlled implementation choices and depart from literal historical reproduction. Trainer's [documentation](https://huggingface.co/docs/transformers/en/main_classes/trainer) describes the accumulation, scheduling, saving and precision controls; pin and log the actual versions used.

First run 50 optimizer steps on a train-only smoke subset to measure peak GPU memory and step time and test evaluation/export. Reset model initialization and optimizer afterward; never fold smoke-run updates into the measured full run. Proceed to DistilBERT one epoch, then RoBERTa up to three epochs only if projected remaining work fits the cap. Stop and report an incomplete run if it does not. Retain epoch metrics and final/best checkpoints as safetensors with explicit label maps, versions, dataset revision and selected-step metadata. Measure rather than assert runtime or speed advantage.

Keep the already completed product benchmark unchanged. Follow its existing validation/test separation; no tuning on reviewed final-test results. Report IMDb validation reproduction separately from performance on that product benchmark, and preserve the existing baselines. Proceed to more training only if the observed product gain justifies it; a higher weighted IMDb F1 by itself does not.
